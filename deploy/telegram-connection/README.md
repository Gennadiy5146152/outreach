# Telegram-профили в Outreach

Раздел «Мессенджеры» управляет несколькими одновременно подключёнными
MTProto-профилями. У каждого отдельная сессия, дневной лимит, окно отправки
по Москве и пауза. Лимит включает попытки отправки этого профиля. При ошибке
Telegram rate-limit отменяются только ожидающие задания соответствующего
профиля. Общее прекращение рассылки отменяет очередь всех профилей и
инвалидирует ранее подготовленные запуски. История, проверка получателя,
стоп-лист и запрет повторного касания за 30 дней общие.

## Подключение

1. Примените миграции основного приложения, включая `024_telegram_profiles.sql`.
   Существующие отправители и задания сохраняются; лимит остаётся 10,
   окно 09:30–11:30 МСК. Новый профиль создаётся на паузе.
2. Добавьте `@username` в «Мессенджерах» или через `telegram_profile_create`.
3. Авторизуйте новый профиль интерактивно в локальном Терминале:

   ```sh
   python -B login.py --account second_username --output-dir /safe/local/directory
   ```

   Скрипт использует Telethon из Dockerfile. Введите API ID/hash приложения
   Telegram, телефон, код и пароль двухэтапной проверки, если он установлен.
   `--app-config /safe/existing/config.json` позволяет повторно использовать
   API ID/hash приложения без копирования старой пользовательской сессии.
   Секреты и коды никогда не передаются через MCP, чат или веб-форму сервиса.
   Скрипт проверяет имя вошедшего пользователя и не перезаписывает существующий файл.
4. Без вывода содержимого передайте созданный `second_username.json` по SSH/SFTP
   в `/root/.local/share/outreach-telegram/` на сервере. Каталог и файлы должны
   читаться только владельцем: UID/GID 65532, режим каталога 0700, файлов 0400.
5. Соберите и запустите сервис `telegram` с профилем compose `telegram`.
   В контейнер каталог монтируется только для чтения. Путь задаётся переменной
   `OUTREACH_TELEGRAM_SESSION_DIR`; секреты не монтируются в веб-сервис.
   Совместимость: `session.json` используется только для legacy-профиля
   `OUTREACH_TELEGRAM_ACCOUNT` (по умолчанию `ideamen51`). Остальные профили
   используют исключительно собственный `<username>.json`.

Менеджер подхватит новую сессию в течение 10 секунд. В списке появятся
«Подключён» и heartbeat. Включение отправки требует отдельного подтверждения
настроек, а запуск конкретной партии требует просмотра получателей, текстов
и расписания. Один профиль нельзя запустить двумя обработчиками одновременно.
Связь с Telegram проверяется по username и сохранённому числовому ID аккаунта.

## MCP

- `telegram_profiles_list` — безопасные состояния и счётчики без сессий.
- `telegram_profile_create` — регистрация на паузе, без отправки.
- `telegram_profile_settings_prepare` / `telegram_profile_settings_execute` —
  лимит, окно и пауза выбранного профиля с явным подтверждением.
- `messenger_drafts_list`, `messenger_draft_get`, `messenger_draft_update` —
  фактура и тексты получателей.
- `telegram_queue_list` — тексты и история, фильтры `sender`, `status`, пагинация.
- `telegram_launch_prepare` / `telegram_launch_execute` — подготовка и запуск
  точной партии от выбранного отправителя. Подготовка ничего не отправляет.
  Для двух окон на заданную дату: `start_date: "2026-11-25"`,
  `windows: [{start:"09:30",end:"11:30",count:10},{start:"17:00",end:"19:00",count:10}]`.
  Сумма count должна совпадать с числом прошедших проверки получателей и не
  превышать дневной лимит профиля. На эту дату не должно быть других заданий
  или попыток отправки. После подтверждения окна сохраняются как разовое
  исключение даты, а каждому сообщению задаётся крайний срок своего окна.
  Пропущенное утро не догоняется вечером; настройки других дат не меняются.
- `telegram_queue_resume_prepare` / `telegram_queue_resume_execute` — перенос
  существующей неотправленной очереди и снятие паузы одним подтверждением.
  Подготовка повторно проверяет стоп-лист и дубли, берёт актуальный текст
  проверенной карточки и показывает старую копию в `previous_body` с признаком
  `body_changed`. Карточки на проверке и изменённые адресаты исключаются.
  Execute ещё раз сверяет текст и только после нового подтверждения обновляет
  копию в очереди. Идентификатор доставки, получатель и основание согласия сохраняются.
  `today_windows` задаёт отдельные интервалы на сегодня (`start`, `end`, `count`);
  `daily_limit` при необходимости меняет постоянный лимит профиля вместе с очередью;
  разовые окна действуют только сегодня. С завтрашнего дня автоматически
  используются обычные лимит и окно профиля. Пропущенное отдельное окно
  не догоняется позднее: для каждого задания сохраняется крайнее время отправки.

Каждый получатель запуска содержит `draft_id`, числовой `recipient_id`,
`permission_kind` (`request` или `consent`) и `permission_evidence` — где
зафиксированы запрос/согласие. Имя Telegram перед отправкой сверяется с ID;
смена владельца имени блокирует отправку. Публичность контакта сама по себе
не является основанием согласия. Покажите пользователю весь подготовленный
план и вызовите execute только после его явного одобрения.

Токены подготовки одноразовые, действуют 10 минут и не переживают перезапуск
веб-сервиса. Изменение текста, настроек, появление дубля или занятый лимит
отклоняет весь запуск. Новые партии автоматически распределяются по свободным
слотам; существующие задания не переназначаются при изменении настроек.
После паузы/уменьшения окна проверьте просроченные задания: обработчик не
догоняет пропущенные дни. `uncertain` требует ручной сверки с перепиской;
автоматического повторения неизвестного результата нет.

## Проверка

```sh
python -B -m unittest discover -s deploy/telegram-connection -p 'test_*.py'
node --test tests/telegram-profiles.test.js
TELEGRAM_TEST_DATABASE_URL=postgres://.../outreach_test npm run test:telegram:db
TELEGRAM_REFRESH_TEST_DATABASE_URL=postgres://.../outreach_refresh_test node --test tests/telegram-queue-refresh-db.test.js
```

Последняя команда требует отдельной пустой тестовой базы и применяет все
миграции. Проверяет перенос старой очереди, независимость профилей, общий
стоп-лист, дубли, одноразовые подтверждения, изменённый текст и общую остановку.
