# Audio/video archive and response-time analytics

User requests: persist audio/video from tracked outreach conversations, retain timestamps from both participants, control response speed in elapsed OR working time with configurable working hours, and expose all analytics through scoped MCP. Existing text timestamps are persisted; existing semantic conversions and deferred-date features must keep working.

## Scope and constraints

Only verified recipients after a confirmed service delivery, exact owner/campaign/job/message context. Never arbitrary chat history, contacts, sessions, or new client sends. Store voice, audio files, video and round video notes in private durable server storage. No external transcription or media service. Retain original Telegram timestamps where available; label historical service receipt timestamps honestly. No body/campaign/job approval changes or automatic semantic success inferred from media. Follow-up dates remain manual.

Server storage is constrained (50GB root, about2.4GB free before build-cache cleanup). Do not fill the root disk: known-size reservation, minimum free-space floor, per-file cap, durable visible pending/failed states rather than claiming success. Never delete customer media automatically. Download outside SQL delivery/reply locks and event callbacks, with resumable durable queue state. File path generated from server UUIDs only, never supplied filename. Worker owns data, web has read-only access through shared group, sessions never mounted into web. API authenticates owner+campaign+job for every file; no public static media routes or embedded credentials. Support authenticated byte ranges for playback; prevent path/symlink escape. FloodWait must defer account RPCs until expiry without a new send/queue-cancel authority.

## Response semantics

Campaign-specific calendar, timezone Europe/Moscow, configurable weekdays and one daily HH:MM opening/closing window (start<end); proposed initial editable display09:00–18:00 Mon–Fri. This is an analysis calendar, separate from delivery windows, never changes outreach schedule/limits. Both elapsed and working durations are calculated for every pair; a mode filter controls visible aggregates. Working duration is the intersection with configured weekday intervals, excluding nights/weekends; no invented holiday calendar.

An Artem response episode starts at the first unresponded inbound message. Consecutive client messages do not reset the start; the first subsequent outbound closes it. Subsequent outbound messages do not create another episode. Audio/video also count as messages. Pending episodes show age, not zero response time; label neutrally as “last message from client / no following response” because an acknowledgement may need no reply. Exclude and expose timestamp anomalies rather than fabricating zero latency. Sort by Telegram message ID, not ingestion order. Separately measure initial client response after first service message, without mixing its denominator into Artem speed.

Response analysis filters use the Moscow day of episode start, explicitly distinct from conversion first-delivery cohorts. Include date/source filters, median/p90 answered response times, answered/pending counts, per-contact episodes, per-day/group breakdowns, oldest pending, exact source timestamps, both duration modes and calendar in API. Settings owner-only; read tools scoped by owner/campaign/read permission. All requested analytics available via MCP, not UI only.

## Delivery and validation

Real-DB tests for tenant isolation, revoked permissions, owner-only calendar updates without campaign revision/delivery changes, exact burst pairing and midnight/weekend/overnight waiting. Fake Telegram network tests for normal/voice/round files, out-of-scope rejection, atomic writes/retry/disk pressure/FloodWait, no long SQL locks, restart recovery and no duplicate sends. Private file-route ownership/path/range tests. Real browser mode/calendar/player/filter/mobile checks. Independent design/task/final review. Deploy reviewed web/migrations and explicitly rebuild/restart only the cabinet Telegram worker after checking no in-flight delivery; verify new worker identity/heartbeat, data and new MCP tools, no client test sends. Update existing agent documentation/instructions where new analytics/media metadata affect review, preserving its schedule and manual follow-up date policy.

## Builder-review rulings

Pair across all verified sent jobs per campaign/connection/recipient before filtering, source from first verified delivery. Calendar edits recompute historical working durations, with schedule revision and one as_of per report. Provenance is persisted in migration036: historical service anchors remain service_receipt; future sends use actual Telegram result date if present. Durable media metadata/queue insert shares the short message transaction, downloads never hold SQL transactions/reply locks. One global active downloader guarded by a dedicated session advisory lock; UUID per-lease partial files; global free floor2GiB, configurable default per-file cap4GiB, unknown sizes visibly deferred, progressive free/size checks. Separate persisted RPC cooldown checked before media and send calls, never CabinetWorker.pause for media. A bounded discovery pass may fetch only exact already-imported private message IDs, no arbitrary history, and must not relabel historical anchor timestamps. Authenticated file serving opens regular files O_NOFOLLOW before streaming, permits valid single ranges only, emits no-store/nosniff and safe MIME. Shared private media directory uses worker UID65532/shared GID1000, web reads only; session volume remains worker-only.
