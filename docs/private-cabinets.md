# Личные кабинеты и Telegram через ограниченный MCP

Личные кабинеты отделены от общего кабинета внутри того же приложения. Существующие почтовые кампании, SMTP/IMAP и общий Telegram-профиль продолжают работать в прежних таблицах. Миграции `026_private_cabinets.sql` и `027_cabinet_email_auth.sql` добавляют таблицы и необязательные поля без переноса личных сессий или переписки в общий кабинет.

## Что доступно владельцу

Короткая инструкция для подключения Telegram и выдачи только отправки/чтения:

1. Откройте https://outreach.korotkov.dev/login.html и войдите в свой кабинет. Если кабинета нет, зарегистрируйтесь и подтвердите email.
2. В разделе **Telegram** введите свой `@username` и нажмите **«Получить QR»**. Если профиль уже есть, нажмите **«Войти по QR»** у него. Для другого аккаунта используйте **«Добавить профиль»**.
3. Откройте страницу с QR на компьютере. На телефоне в Telegram выберите **Настройки → Устройства → Подключить устройство** и отсканируйте код. Если потребуется, введите облачный пароль в кабинете. Дождитесь статуса **«Подключён»**. Если код истёк, нажмите **«Получить новый QR»**. При коротком обрыве связи страница повторяет проверку автоматически.
4. В разделе **«Доступы MCP»** задайте название и срок токена. Отметьте только **«Читать черновики, очередь и ответы рассылок»** и **«Готовить и запускать сохранённые сообщения»**. Остальные галочки снимите. Если помощник также должен останавливать очередь, дополнительно выдайте **«Останавливать сообщения»**.
5. В **«Область доступа»** выберите **«Все рассылки кабинета»**. Это общий токен на существующие и будущие рассылки; создавать рассылку заранее не нужно. Для ограниченного доступа можно выбрать **«Только выбранные рассылки»** и отметить нужные.
6. Нажмите **«Создать токен»**, скопируйте его и вставьте в защищённые настройки MCP как `MCP_API_TOKEN`; `OUTREACH_BASE_URL=https://outreach.korotkov.dev`. Сам токен в обычную переписку не отправляйте. Он показывается один раз.

Такой токен читает черновики, очередь и сохранённые сообщения **всех разрешённых ему рассылок**, а не только сообщения, отправленные именно этим токеном. Из входящих сохраняются привязанные ответы через Telegram «Ответить» на сообщения сервиса и их цепочку; обычная реплика без такой связи может не попасть в MCP. Общий список личных диалогов, посторонняя история и Telegram-сессия через MCP недоступны. Запуск требует подготовки точного плана и подтверждения владельцем.

Область доступа задаётся при создании токена: `campaign_access: "all"` сохраняет `all_campaigns=true` и пустой `campaign_ids`; `campaign_access: "selected"` (по умолчанию в API для совместимости) сохраняет прежний список. Старые токены не расширяются. В обоих режимах запросы проверяют `owner_id`, scopes, отзыв/срок действия и подтверждение отправки. Область доступа не даёт прав владельца кабинета на QR, управление токенами или другие кабинеты. `/mcp/context` и `cabinet_access` возвращают `all_campaigns`, чтобы клиент различал общий доступ и пустой список.

Это ограничение MCP, а не ограничение прав владельца сервера: Telegram-сессия хранится на сервере, его администратор имеет технический доступ.

1. Пользователь открывает `/login.html`, выбирает «Создать кабинет», указывает имя и email. Письмо содержит одноразовую ссылку на 1 час. Пароль задаётся **после** подтверждения почты; до этого аккаунт не создаётся. Так нельзя заранее зарегистрировать чужую почту с известным атакующему паролем. Войти можно по подтверждённому email. Дополнительно администратор может создавать приглашения в `/cabinet-admin` на 24 часа: пользователь задаёт пароль самостоятельно и затем привязывает email в своём кабинете. Пароли хранятся как salted scrypt hashes; сессия — случайный, отзываемый токен в HttpOnly/SameSite=Strict cookie на 12 часов.
2. Пользователь открывает `/cabinet`, подключает свой Telegram по QR. При включённой двухфакторной аутентификации вводит облачный пароль на этой же странице. Для подключения требуется публичный username; после входа проверяются username и числовой ID.
3. Создаёт рассылку с лимитом и окном отправки по МСК, сохраняет черновики. Импорт — JSON-массив до 500 объектов; частичный импорт показывает число сохранённых записей. Повторные контакты внутри одной рассылки отклоняются.
4. Выбирает черновики, получает точные тексты, получателей и расписание, подтверждает запуск. Подготовка ничего не отправляет. План живёт 10 минут, привязан к текущей сессии/токену и выполняется один раз. Изменение текста, настроек, состава очереди или остановка аннулирует старый план.
5. Отдельно создаёт MCP-токен для конкретных рассылок и прав, на 1–90 дней. Токен показывается один раз, в базе хранится SHA-256 hash. Его можно отозвать. Отзыв закрывает дальнейшие MCP-запросы; уже одобренную очередь останавливают отдельно.

Права:

| Право | Доступ |
|---|---|
| `outreach:read` | Черновики, очередь, сохранённые исходящие и ответы разрешённых рассылок |
| `outreach:draft` | Создание черновиков, изменение текста до постановки в очередь; при `all_campaigns=true` также выбор существующего отправителя и создание пустой рассылки на паузе |
| `outreach:send` | Подготовка и подтверждение запуска сохранённых черновиков |
| `outreach:stop` | Подготовка и подтверждение остановки выбранных черновиков |

Для исходного запроса достаточно `read`, `send`, `stop`; редактирование можно не выдавать. Право отправки позволяет видеть точный текст в превью плана. Сами права неизменяемы: для другой комбинации создаётся новый токен. Вход владельца нужен для выдачи/отзыва токенов и подключения Telegram; токен MCP не может сделать это сам.

### Создание рассылки без пароля владельца

Токену с `outreach:draft` и областью «Все рассылки кабинета» доступны `campaign_connections_list` и `campaign_create`. Первая команда показывает только ID, название, username и статус собственных подключений для выбора отправителя. QR, пароли, файлы сессии, числовой ID Telegram и переписка не выдаются; подключить или отключить Telegram по-прежнему может только владелец.

`campaign_create` принимает `connection_id`, `name`, `daily_limit` (по умолчанию 10), `window_start` (09:30) и `window_end` (11:30), время по Москве. Создаётся пустая рассылка на паузе без заданий отправки. Применяются существующие проверки владельца подключения, расписания, отзыва и срока токена. Токены с доступом только к выбранным рассылкам, а также токены без `outreach:draft`, эти команды не получают; HTTP API также проверяет эти ограничения. Создание отражается в журнале кабинета.

После создания черновики сохраняются через `draft_create`. Публичный контакт не подменяет основание обращения. Отправка остаётся отдельным действием: prepare → показать полный план → явное разрешение → execute.

## Восстановление по почте

«Забыли пароль?» отправляет одноразовую ссылку на 30 минут. Ответ одинаков для известного и неизвестного адреса, токены в API и журналах не выдаются. В БД хранится только hash ссылки. Ограничения: до 3 писем одного назначения на email за 15 минут и общий лимит попыток по IP. Ссылки находятся во фрагменте URL, очищаются из адресной строки и не попадают в HTTP access log.

У пользователя после сброса отзываются все сеансы и MCP-токены, очередь его кабинета останавливается. Более старые ссылки сброса перестают работать. Подключение Telegram остаётся его собственным; новый доступ MCP он выдаёт сам.

Для текущего административного входа адрес восстановления — `team@korotkov.dev`, по выбору владельца. До первого сброса продолжает работать прежний пароль. После сброса новый scrypt hash хранится в `cabinet_admin_recovery`; старый пароль из окружения больше не принимается. Ревизия авторизации аннулирует старые браузерные cookie, сохраняется в БД и учитывается после перезапуска. Существующий административный API-ключ независим от браузерного пароля и автоматически не меняется. Саморегистрация по почте всегда создаёт обычный изолированный кабинет, административные права через неё не выдаются.

Служебные письма отправляются через выбранный SMTP-ящик отдельно от кампаний: без трекинга, фоллоу-апов и записи в маркетинговую очередь. Они отправляются и при dry-run аутрича, поскольку являются частью запрошенного входа/восстановления. Сбой SMTP не раскрывает адрес/токен; ссылка помечается использованной, пользователь может запросить новую.

## Граница приватности

Сессия MTProto имеет полномочия полноценного аккаунта Telegram. Она хранится на сервере, как согласовано с владельцем; администратор сервера остаётся доверенным. Это изоляция пользователей и API, а не защита от администратора/root.

Файл сессии находится в отдельном Docker volume, смонтированном только в `cabinet-telegram`. Web, MCP и общий Telegram-обработчик не получают этот volume. Worker работает без root, с read-only root filesystem, без capabilities. Web хранит только временный QR и зашифрованный AES-GCM облачный пароль для передачи обработчику; после попытки входа или отмены пароль очищается. Session/API hash/облачный пароль никогда не возвращаются через MCP.

Обработчик не экспортирует диалоги, контакты и общую историю. В БД попадают:

- исходящее сообщение, отправленное по подтверждённому заданию сервиса;
- входящее личное сообщение от того же числового Telegram ID, если `reply_to` указывает на уже сохранённое сообщение этой цепочки.

**Обычные сообщения без «Ответить» не импортируются.** Владелец проверяет их в Telegram самостоятельно. Это намеренная граница: близкое время или совпадение собеседника не доказывает, что личное сообщение относится к аутричу. Медиа не скачиваются. При восстановлении соединения используется механизм обновлений Telethon; полнота восстановления пропущенных обновлений не гарантируется Telegram, общего чтения истории нет.

Кабинетный cookie не открывает старые `/api/*` общего кабинета. Токены `ocp_` отвергаются старым API даже при наличии администраторского cookie. Все запросы нового API получают owner ID из аутентификации, проверяют campaign allowlist и scope. Ограничения связей закреплены составными FK в PostgreSQL. Триггеры и блокировка идентичности не позволяют одновременно закрепить один Telegram ID за старым и личным обработчиками. Пустая старая карточка без сессии входу не мешает.

## Очередь и ошибки

По будням, заданное окно МСК, интервалы 3–10 минут. Дневной лимит общий для одного подключения по всем его рассылкам, учитываются попытки, включая неудачные. Для рассылок одного подключения требуются одинаковые лимит и окно. Это максимум, а не гарантия заполнить все слоты при сбоях/задержках.

Проверка username → числовой ID происходит перед отправкой: переименование/переуступка username не перенаправит сообщение другому человеку. В очередь записывается неизменяемый текст и стабильный Telegram `random_id`. Неопределённый результат после обрыва или рестарта становится `uncertain`; автоматического повторения нет, оставшаяся очередь при неопределённости или rate limit отменяется, рассылки ставятся на паузу. Обход ограничений Telegram не выполняется.

Для отдельно согласованной отправки сегодня доступна пара MCP `telegram_one_off_prepare` / `telegram_one_off_execute`. Подготовка принимает максимум два конкретных черновика и окно `window_start` / `window_end` на текущий московский день. Нужны одновременно `outreach:send`, `outreach:draft` и доступ ко всем рассылкам владельца; у подключения не должно быть `queued`, `sending` или `uncertain`. Полный план с получателями, текстами и временем нужно показать человеку и получить новое явное одобрение до execute. План действует 10 минут; его точные слоты не переносятся после истечения.

Без `daily_limit` этот план разрешает только выбранным заданиям потолок обычного лимита плюс два, максимум 100, сохраняя настройки кампании. Необязательный `daily_limit` явно показывает в плане постоянную смену дневного лимита и использует это значение как потолок, без дополнительных двух сообщений. Обычное окно остаётся прежним; изменение должно помещаться в него и быть совместимым с другими кампаниями подключения. Истёкшие задания отменяются с `one_off_window_expired` и на следующий день не переносятся. Перед использованием этой функции обязательно обновить не только web и БД, но и образ `cabinet-telegram` по командам ниже: старый обработчик не применяет эти поля.

Отключение Telegram владельцем отменяет очередь и отзывает текущую сессию на стороне Telegram при доступности Telegram/обработчика. Неактивный обработчик не сможет отправлять по отключённому профилю после старта. Отключение кабинета администратором отзывает cookie и токены, отменяет очередь и подключение. Общая кнопка «Остановить всю рассылку» включает новый контур и аннулирует подготовленные планы; остановка ждёт уже выполняющийся запрос отправки, отправленное сообщение не отзывается.

## Развёртывание

Основной адрес существующего сервиса — **https://outreach.korotkov.dev**: общий вход `/login.html`, кабинеты пользователей `/cabinet`, управление пользователями `/cabinet-admin`. Старый HTTP-адрес на IP не использовать для входа и передачи токенов. В основном `.env`:

```dotenv
CABINET_PUBLIC_URL=https://outreach.korotkov.dev
CABINET_ALLOW_HTTP=false
AUTH_COOKIE_SECURE=true
CABINET_SIGNUP_ENABLED=true
CABINET_AUTH_MAILBOX_EMAIL=team@korotkov.dev
AUTH_RECOVERY_EMAIL=team@korotkov.dev
```

HTTPS обслуживает существующий обратный прокси. Ниже пример настройки для нового развёртывания; отдельное приложение или перенос БД не нужны.

В основном `.env`:

```dotenv
CABINET_PUBLIC_URL=https://YOUR_OUTREACH_DOMAIN
CABINET_ALLOW_HTTP=false
AUTH_COOKIE_SECURE=true
# Только фактические адреса прокси / CIDR. Не доверяйте произвольным клиентам.
TRUST_PROXY=loopback
CABINET_SECRET=<случайный секрет минимум 32 символа>
CABINET_TELEGRAM_API_ID=<application id с my.telegram.org>
CABINET_TELEGRAM_API_HASH=<application hash с my.telegram.org>
CABINET_TELEGRAM_SEND_ENABLED=false
```

API ID/hash — реквизиты Telegram-приложения, не пароль Telegram и не токен бота. Секреты вводятся на сервере/в защищённом хранилище, не в исходном коде. Прокси должен передавать Host и X-Forwarded-Proto; прямой внешний доступ к приложению следует закрыть, оставив разрешённые адреса прокси. Для Docker-прокси `loopback` недостаточно: задайте фактическую доверенную сеть прокси. Общий вход использует Secure cookies, поэтому после переключения открывайте и общий кабинет через HTTPS.

После резервной копии БД примените штатную миграцию и обновите web. Соберите и включите отдельный обработчик:

```sh
docker compose -f docker-compose.prod.yml --profile cabinet-telegram build cabinet-telegram
docker compose -f docker-compose.prod.yml --profile cabinet-telegram up -d cabinet-telegram
```

По умолчанию `CABINET_TELEGRAM_SEND_ENABLED=false` в web и worker: QR и черновики доступны, отправка блокируется. После проверки HTTPS, изоляции и подключения измените флаг на `true` в основном `.env` и пересоздайте web и `cabinet-telegram`. Это разрешает обработчику выполнять **только отдельно подтверждённые** задания. Запуск worker сам не создаёт сообщений. Не запускайте второй worker на тот же volume; PostgreSQL дополнительно ограничивает один активный обработчик подключения.

### MCP

Тот же локальный адаптер автоматически выбирает ограниченный сервер по префиксу токена:

```json
{
  "command": "node",
  "args": ["/ABSOLUTE/PATH/outreach/src/mcp/server.js"],
  "env": {
    "OUTREACH_BASE_URL": "http://213.171.10.147:3000",
    "OUTREACH_ALLOW_HTTP": "true",
    "MCP_API_TOKEN": "ocp_<токен владельца>"
  }
}
```

Вставьте токен в настройки MCP локально. Для текущего HTTP-адреса требуется явное `OUTREACH_ALLOW_HTTP=true`; без него удалённый адрес допускается только по HTTPS. На старте адаптер получает scope/allowlist и публикует только разрешённые инструменты. Каждый последующий HTTP-запрос проверяет токен заново, поэтому отзыв/истечение действует и для уже запущенного адаптера. Правило MCP: prepare → показать полный план человеку → получить разрешение → execute. API технически требует действующий план, но не может проверить содержание разговора с человеком; агент обязан соблюдать этот порядок.

## Проверка без реальной отправки

Используйте только отдельную локальную БД `cabinet_test` или `cabinet_test_verify`, никогда production. Тесты удаляют созданные кабинетные данные из этой БД. Миграции должны быть применены заранее:

```sh
DATABASE_URL=postgres://postgres:TEST_PASSWORD@127.0.0.1:5432/cabinet_test npm run migrate
CABINET_TEST_DATABASE_URL=postgres://postgres:TEST_PASSWORD@127.0.0.1:5432/cabinet_test npm run test:cabinet
python3 -m venv .tmp/cabinet-test-venv
.tmp/cabinet-test-venv/bin/pip install -r deploy/telegram-connection/requirements.txt
CABINET_TEST_DATABASE_URL=postgres://postgres:TEST_PASSWORD@127.0.0.1:5432/cabinet_test .tmp/cabinet-test-venv/bin/python -B -m unittest discover -s tests -p cabinet_worker_test.py -v
```

HTTP/PostgreSQL проверка использует двух пользователей и разные токены, чужие IDs, CSRF, сроки, отзыв, неизменность превью, однократное выполнение, остановку, гонку присвоения Telegram ID и отключение пользователя. Python использует настоящий PostgreSQL с поддельным Telegram RPC: никакие сообщения в Telegram не отправляются. Отдельно проверяются QR/2FA/истечение, граница импорта ответов, переуступка username, суточный лимит, пауза и неопределённая доставка.
