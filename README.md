# Outreach Desk

Локальный сервис для личного B2B-аутрича по ТЗ: Node.js, PostgreSQL, SMTP/IMAP, безопасная email-валидация, прогрев, open tracking, вложения и аналитика.

## Быстрый старт

1. Скопируйте настройки:

```bash
cp .env.example .env
```

2. Задайте логин и пароль для входа:

```dotenv
AUTH_USER=admin
AUTH_PASSWORD=сложный_пароль
AUTH_SESSION_SECRET=длинная_случайная_строка
```

Если сервис открыт через обычный `http://IP:3000`, оставьте `AUTH_COOKIE_SECURE=false`. Для HTTPS можно поставить `true`.

3. Запустите сервис:

```bash
docker compose up -d
```

4. Откройте:

```text
http://localhost:3000
```

По умолчанию включен безопасный dry-run: письма логируются и сохраняются в БД, но не уходят через SMTP. Для реальной отправки заполните SMTP/IMAP-настройки mailbox в UI и переключите режим в разделе `Настройки`.

## Что открывать первым

Откройте раздел `Старт`. Это главный экран для первичной настройки. Он показывает:

- что уже готово;
- что еще мешает запуску;
- куда нажать следующим шагом;
- включен ли безопасный dry-run режим.

Если непонятно, что делать: ничего не ищите по меню, просто откройте `Что делать` и нажимайте кнопку в блоке `Сейчас сделай это`.

На этом же экране есть блок `Что нужно заполнить в .env`: он показывает обязательные переменные, пароли mailbox и готовый шаблон строк для локального `.env`.

## Что значит каждый раздел

- `Старт` — пошаговый чеклист запуска.
- `Обзор` — главные цифры: лиды, отправки, открытия, ответы.
- `База` — добавление лидов, CSV-импорт, валидация email.
- `Почта` — подключение SMTP/IMAP, проверка доступов и SPF/DKIM/DMARC.
- `Прогрев` — прогревочные письма между вашими mailbox.
- `Кампании` — шаблоны, HTML-письма, вложения, preflight, тестовый запуск.
- `Очередь` — что будет отправлено, когда, прогресс, ETA и ошибки.
- `Входящие` — ответы из IMAP и ручная правка классификации.
- `Стоп-лист` — email и домены, которым нельзя писать.
- `События` — технический журнал действий.
- `Настройки` — текущий runtime: dry-run, общий суточный лимит outreach, tracking URL, лимиты вложений.

## Как начать прогрев и рассылки

### 1. Подключите mailbox

Откройте `Почта` и добавьте 2 ящика. Пароль почты вводится прямо в форме: сервис сам сохранит его в локальный `.env` в переменную вида `MAILBOX_NAME_DOMAIN_RU_PASSWORD`, а в базе оставит только имя этой переменной.

Для Яндекса обычно нужен пароль приложения, а не основной пароль аккаунта. Настройки:

```text
SMTP host: smtp.yandex.ru
SMTP port: 465
IMAP host: imap.yandex.ru
IMAP port: 993
Secure: true
```

После сохранения нажмите `Проверить`: сервис проверит SMTP, IMAP и MX/SPF/DKIM/DMARC домена.

### 2. Включите прогрев

В разделе `Прогрев` включите прогрев для обоих mailbox и нажмите `Отправить warmup сейчас`, либо дождитесь worker. Warmup отправляется только между вашими подключенными mailbox.

### 3. Подготовьте кампанию

1. Импортируйте или добавьте лидов.
2. Запустите валидацию.
3. Создайте кампанию.
4. Создайте шаги письма.
5. При необходимости загрузите вложения к шагу.
6. Добавьте valid/risky лидов в кампанию.
7. Запустите `Preflight`.
8. Сначала запустите `Тест`, затем `Старт manual` или `Старт auto`.

### 4. Включите реальную отправку

Когда тестовый сценарий прошел, откройте `Настройки` и переключите `Отправка` в режим `Реальная отправка`.

Runtime-настройки хранятся в PostgreSQL и применяются без пересоздания контейнеров.

### Суточный лимит outreach на один почтовый ящик

В `Настройки` → `Лимит outreach на один ящик в сутки` задаётся предел отдельно для каждого mailbox. По умолчанию каждый почтовый ящик может отправить до 100 реальных писем за календарные сутки в часовом поясе приложения. Индивидуальный `Лимит рассылки в день` в карточке mailbox переопределяет это значение для конкретного ящика.

В лимит конкретного ящика вместе входят первые письма и follow-up, отправленные с него. Worker сначала выбирает подошедшие follow-up, а новые первые письма отправляет только на оставшиеся места этого ящика. Например, при 70 follow-up с одного mailbox в этот день с него будет отправлено не больше 30 новых писем. Тестовые письма и технический прогрев в outreach-лимит не входят.

Лимит проверяется при транзакционном резервировании каждого письма. Несколько worker учитывают уже отправленные сообщения и элементы со статусом `running` отдельно для каждого mailbox, поэтому не должны совместно превысить его предел. Более низкий лимит кампании продолжает дополнительно ограничивать отправку.

### 5. Open tracking

Для реальных открытий нужен публичный URL, например через `ngrok` или `cloudflared`.

Укажите публичный адрес в `Настройки` → `Tracking URL`.

## MCP для управления аутричем из Codex

MCP работает локально через `stdio` и обращается к уже запущенному Outreach Desk по HTTP. Поэтому сначала запустите приложение и PostgreSQL:

```bash
docker compose up -d
```

Создайте длинный случайный `MCP_API_TOKEN` и укажите одно и то же значение:

- в локальном `.env`, который читает Outreach Desk;
- в окружении процесса Codex, который запускает MCP.

Минимальные настройки:

```dotenv
MCP_API_TOKEN=длинное-случайное-значение
OUTREACH_BASE_URL=http://127.0.0.1:3000
MCP_CONFIRMATION_TTL_SECONDS=600
MCP_REQUEST_TIMEOUT_MS=15000
```

### Подключение в Codex

Codex хранит локальные MCP-серверы в `~/.codex/config.toml` или в доверенном проектном `.codex/config.toml`. Используйте абсолютные пути:

```toml
[mcp_servers.outreach]
command = "node"
args = ["/absolute/path/to/outreach/src/mcp/server.js"]
cwd = "/absolute/path/to/outreach"
env_vars = ["MCP_API_TOKEN"]
env = { OUTREACH_BASE_URL = "http://127.0.0.1:3000" }
required = true
default_tools_approval_mode = "writes"
```

Перезапустите Codex и проверьте подключение командой `codex mcp list` или `/mcp`. Поля `command`, `args`, `cwd`, `env`, `env_vars` и режим подтверждения соответствуют [официальной документации Codex MCP](https://learn.chatgpt.com/docs/extend/mcp).

Для ручной проверки протокола:

```bash
npx @modelcontextprotocol/inspector node src/mcp/server.js
```

### Правило подтверждения отправки

Отправка и другие существенные действия разделены на два инструмента:

1. `*_prepare` повторно читает состояние Outreach Desk, выполняет preflight и показывает точный план.
2. Codex обязан показать план и спросить ваше разрешение.
3. Только после явного ответа можно вызвать `*_execute` с одноразовым токеном.

Токен действует 10 минут и сгорает при первой попытке выполнения, даже если повторная проверка или HTTP-запрос завершились ошибкой. Если полный текст писем, follow-up, вложения, участники кампании, очередь, mailbox, режим доставки или диалог изменились, выполнение блокируется и требуется новый план. Эта защита действует для запуска, ручных ответов, подтверждения и отмены очереди, stop-list, массовых действий, добавления/паузы/возобновления участников кампаний, останавливающей классификации ответов, управления цепочками и включения реальной отправки.

Для первой проверки оставьте `MAIL_DRY_RUN=true`, вызовите `outreach_status` и убедитесь, что `dryRun` включён. Затем можно импортировать тестовый файл, выполнить `drafts_preflight`, `launch_prepare` и разрешить `launch_execute`: письма пройдут через обычную очередь приложения, но не уйдут наружу.

Пароли mailbox через MCP не добавляются и не возвращаются. Их нужно вводить в веб-интерфейсе Outreach Desk.

## Резервная копия PostgreSQL

```bash
docker compose exec postgres pg_dump -U outreach outreach > backup.sql
```

## Production и автодеплой

После настройки production-инфраструктуры каждый push в `main` сначала проходит
полную проверку в GitHub Actions, а затем разворачивается на сервере по точному
SHA коммита. Сервер перед миграциями создаёт резервную копию PostgreSQL,
проверяет `/api/health` и откатывает приложение при неуспешном запуске.

Подробная настройка, секреты, диагностика и восстановление описаны в
[`deploy/README.md`](deploy/README.md).

Автодеплой не запускает `worker`. Его включают отдельно только после явного
разрешения и проверки очереди, потому что worker может отправлять письма.

## Важное

- `.env` не коммитится.
- Вложения хранятся в `storage/attachments`.
- Open tracking для реальных получателей требует публичный Tracking URL, например через туннель.
- Стоп-лист доступен в UI: адреса и домены из него исключаются из коммуникации.
- Очередь показывает progress, ETA, countdown до следующего письма и ошибки отправки.
